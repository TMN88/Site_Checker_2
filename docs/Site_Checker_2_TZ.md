# Итоговое техническое задание — Site Checker 2.0

**Проект\:** Site Checker 2.0
**Новый репозиторий\:** `TMN88/Site_Checker_2`
**Платформа\:** OpenWrt 24.10.x / 25.12.x
**Интерфейс\:** LuCI → Службы → Site Checker 2.0
**Язык\:** русский
**Версия первого релиза\:** 2.0.0

ТЗ объединяет все согласованные требования с учётом последних уточнений: на роутере устанавливается только один из обходчиков (Podkop, Forcop или Forkozz), диагностика берётся непосредственно из него, а для проверки сайтов используется исключительно механизм Zapret Manager.

# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
# Site Checker 2.0 для OpenWrt

## 1. Назначение проекта

Разработать вторую версию приложения Site Checker — универсальную диагностическую панель OpenWrt.

Приложение должно объединять три основные функции:

1. **Проверка доступности сайтов** — единый механизм, адаптированный из Zapret Manager.
2. **Диагностика обходчика** — автоматическое определение установленного Podkop, Forcop или Forkozz и запуск его родного диагностического механизма.
3. **«Куда пойдёт запрос»** — проверка предполагаемого маршрута домена или IP-адреса, используя механизм Forkozz.

Приложение не должно управлять настройками VPN, изменять firewall или автоматически исправлять выявленные проблемы.

Все проверки запускаются пользователем вручную.

## 3. Проверка доступности сайтов

### 3.1. Единый механизм проверки

Полностью отказаться от двух независимых таблиц предыдущей версии.

Оставить **один механизм**, основанный на реализации проверки сайтов Zapret Manager:

https://github.com/StressOzz/Zapret-Manager

Изучить исходники диагностической проверки сайтов, включая `_test_prepare_urls()` и `_si_sites()`.

Перенести алгоритм в самостоятельный модуль Site Checker 2.0.

Не требовать установленного Zapret Manager.

### 3.2. Требования к механизму

- Использование диапазона байтов `0–65535`, как предусмотрено исходным механизмом.
- Настраиваемые таймауты.
- Измерение времени ответа.
- Определение HTTP-кода.
- Обработка сетевых ошибок.
- Ограничение числа параллельных запросов.
- Защита от повторного запуска до завершения текущей проверки.

Выполнять проверку с учётом действующей конфигурации сети роутера.

Отображать:

- Название сервиса.
- Статус.
- HTTP-код.
- Время ответа.
- Причину ошибки.

Статусы:

- 🟢 Доступен.
- 🔴 Недоступен.
- 🟡 Ошибка или неопределённый результат.
- ⚪ Не проверялся.

Успешный HTTP-ответ не означает, что все функции сайта работают корректно. Например, доступность главной страницы YouTube не гарантирует воспроизведение видео.

## 4. Диагностика установленного обходчика

### 4.1. Главное архитектурное правило

**На одном роутере может быть установлен только один из трёх поддерживаемых обходчиков:**

- Podkop.
- Forcop (Forkop).
- Forkozz.

Поэтому Site Checker должен определить единственное установленное приложение и получать диагностические данные исключительно из него.

Не запускать диагностику нескольких приложений.

Не использовать диагностику Forcop в качестве универсального механизма для остальных.

### 4.2. Автоматическое обнаружение

При нажатии кнопки **«Запустить диагностику»**:

1. Проверить установленные пакеты и конфигурации.
2. Определить установленное приложение.
3. Определить его версию и состояние.
4. Вызвать родной диагностический механизм.
5. Получить и обработать результаты.
6. Вывести итог.

Если ни одно приложение не обнаружено, показать понятное уведомление.

Если обнаружено более одного приложения, что противоречит ожидаемой конфигурации, вывести диагностическую ошибку, не выбирая произвольный источник.

### 4.3. Источники

| Обходчик | Источник |
|---|---|
| Podkop | Встроенный диагностический блок Podkop |
| Forcop | Встроенный диагностический блок Forcop |
| Forkozz | Встроенный диагностический блок Forkozz |

**Важно:** у Forkozz диагностика реализована несколько иначе, чем у Podkop/Forcop.

Необходимо изучить реальные исходники всех трёх проектов, определить команды, функции и форматы результатов.

Использовать нативную диагностику каждого приложения.

Не заменять её собственными упрощёнными CURL-, ping- или DNS-проверками.

### 4.4. Проверяемые параметры

Из диагностического блока установленного приложения получать:

**А. Версия приложения**

- Установленная версия.
- Доступная актуальная версия.
- Наличие обновления.
- Ошибки проверки обновления.

**Б. Состояние**

- Установлено ли приложение.
- Запущена ли служба.
- Сообщает ли встроенная диагностика об ошибках.

**В. DNS**

- Используемый DNS.
- Корректность работы DNS.
- Соответствие настроек выбранному режиму обходчика.
- Ошибки, найденные родной диагностикой.

**Г. FakeIP**

- Используется ли FakeIP.
- Корректно ли он работает.
- Соответствует ли его состояние конфигурации приложения.
- Обнаружены ли диагностические ошибки.

Отключённый FakeIP не должен автоматически считаться проблемой, если выбранный режим приложения не требует его использования.

**Д. Общий диагностический результат**

- Ошибки.
- Предупреждения.
- Рекомендации, предоставляемые диагностикой приложения.

### 4.5. Отображение результатов

Основное требование: не показывать длинный список успешных проверок.

Если диагностика завершилась успешно и проблем нет:

**✅ ВСЁ ОК**

Если обнаружены проблемы:

```text
Диагностика завершена

⚠️ Доступна новая версия Forcop
🔴 DNS: обнаружена ошибка
🟡 FakeIP: настройки не соответствуют режиму
```

Отображать только обнаруженные недочёты.

Для каждого недочёта предусмотреть короткую рекомендацию.

Если диагностический блок не удалось запустить, показывать ошибку диагностики, а не «ВСЁ ОК».

### 4.6. Ограничения

- Проверка исключительно по кнопке.
- Не выполнять диагностику автоматически при открытии страницы.
- Не запускать фоновые службы.
- Не менять настройки обходчика.
- Не перезапускать его службу.
- Не менять DNS и FakeIP.
- Не устанавливать обновления автоматически.

### 4.7. Архитектура адаптеров

Создать три адаптера:

```text
diagnostics-podkop
diagnostics-forcop
diagnostics-forkozz
```

Активным может быть только один.

Все адаптеры возвращают данные в едином формате для интерфейса Site Checker.

Если конкретное поле недоступно в родной диагностике, не подставлять выдуманное значение. При необходимости предусмотреть безопасное дополнительное получение данных с явным указанием источника.

## 5. Раздел «Куда пойдёт запрос»

### 5.1. Источник механизма

Изучить и адаптировать механизм из Forkozz, вкладка «Подключение», блок **«Куда пойдёт запрос»**.

Референс — предоставленный скриншот Forkozz.

Требуется перенести не только внешний вид, но и реальную логику анализа правил.

При адаптации учитывать, что Site Checker должен работать и на роутерах с Podkop или Forcop.

### 5.2. Функционал

Пользователь вводит:

- Домен.
- IPv4-адрес.
- IPv6-адрес.

После нажатия кнопки «Проверить» приложение анализирует правила и определяет предполагаемый путь запроса.

Результат должен содержать:

- Назначение запроса.
- Правило, по которому он обрабатывается.
- Секцию обходчика, если она определяется.
- Предполагаемый выход через WAN или VPN.
- Причину выбора маршрута.

Поддерживать определение маршрута через AmneziaWG, WARP или другие интерфейсы в пределах реально доступной информации.

Не выдавать предположение за подтверждённый фактический маршрут пакета.

### 5.3. Быстрый выбор сайтов

Под полем ввода разместить кнопки с сайтами из Site Checker.

Пример:

```text
КУДА ПОЙДЁТ ЗАПРОС

[ youtube.com                  ] [Проверить]

[youtube.com] [instagram.com] [discord.com]
[chatgpt.com] [telegram.org] [whatsapp.com]
[остальные выбранные сайты]
```

Требования:

- Кнопки формируются динамически.
- Используется список сайтов из настроек Site Checker.
- Нажатие подставляет домен в поле проверки.
- Сохраняется ручной ввод любого домена/IP.
- Исключённые из проверок сайты не должны отображаться среди быстрых кнопок.

### 5.4. Совместимость с обходчиками

Механизм Forkozz необходимо изучить и адаптировать с учётом:

- Podkop.
- Forcop.
- Forkozz.

Необходимо установить, какие данные маршрутизации доступны для каждого приложения и можно ли использовать общий механизм.

Если для отдельного обходчика полноценный анализ невозможен, честно сообщать об ограничении.

Не подменять механизм анализа правил обычной командой `ip route get`, поскольку она не отражает всю логику доменных списков, FakeIP и перенаправлений.

### 5.5. Безопасность

- Проверка не изменяет правила.
- Не перезапускает VPN.
- Не изменяет сетевые интерфейсы.
- Не сохраняет конфиденциальные данные.
- Выполняет валидацию введённого домена/IP.
- Исключает shell-инъекции.

## 6. Новый интерфейс Site Checker 2.0

### 6.1. Референсы

**Компоновка и расположение элементов:** Forkozz.

**Цвета и визуальный стиль:** YouTube Watchdog и другие наши проекты LuCI.

Цель — современный компактный интерфейс с хорошо читаемыми состояниями, кнопками и таблицами.

### 6.2. Темы

Реализовать:

- Тёмную тему.
- Светлую тему.
- Неоновые акценты.
- Автоматическое согласование с активной темой LuCI там, где это возможно.

Цветовая схема:

| Элемент | Цвет |
|---|---|
| Основной акцент | Неоновый голубой |
| Вторичный акцент | Фиолетовый |
| Успех | Зелёный |
| Предупреждение | Янтарный |
| Ошибка | Красный |
| Фон тёмной темы | Графитовый |
| Фон светлой темы | Светло-серый / белый |

Не допускать конфликтов оформления с Argon, Footstrap, Aurora и стандартными темами LuCI.

### 6.3. Структура страницы

Предусмотреть три вкладки:

**Вкладка 1 — Сайты**

- Кнопка «Проверить сейчас».
- Таблица сайтов.
- Настройки выбора сайтов.
- HTTP-коды и задержки.
- Статусы доступности.

**Вкладка 2 — Диагностика**

- Кнопка «Запустить диагностику».
- Название обнаруженного обходчика.
- Результат «ВСЁ ОК» или список только недочётов.
- Рекомендации по найденным проблемам.

**Вкладка 3 — Куда пойдёт запрос**

- Поле ввода назначения.
- Кнопка «Проверить».
- Быстрые кнопки сайтов.
- Результат анализа маршрута.
- Информация о сработавших правилах.

Переключение вкладок не должно запускать сетевых операций.

### 6.4. Адаптивность

Интерфейс должен корректно работать:

- На компьютере.
- На планшете.
- На телефоне.

На узком экране кнопки и поля должны переноситься, не выходя за пределы панелей.

## 7. Установщик

Создать единый установочный скрипт:

`install.sh`

После публикации он должен запускаться командой:

```sh
wget -O /tmp/site-checker-2-install.sh \
https://raw.githubusercontent.com/TMN88/Site_Checker_2/main/install.sh \
&& sh /tmp/site-checker-2-install.sh
```

Функции установщика:

1. Определить OpenWrt и архитектуру.
2. Определить `apk` или `opkg`.
3. Проверить зависимости.
4. Установить только необходимые пакеты.
5. Разместить файлы Site Checker 2.0.
6. Зарегистрировать меню LuCI.
7. Обновить кэш меню.
8. Проверить успешность установки.
9. Вывести итоговый статус.

Предусмотреть обновление приложения без потери настроек.

Создать отдельный сценарий удаления.

**Запрещено удалять или изменять Podkop, Forcop, Forkozz, Zapret Manager, AWG и другие сетевые приложения.**

## 8. Производительность

- Не создавать постоянно работающий демон.
- Не создавать cron-задачи.
- Не запускать проверки при загрузке интерфейса.
- Использовать ограниченное количество параллельных CURL-запросов.
- Ограничить время выполнения проверок.
- Не допускать одновременно запущенных дублирующих процессов.
- Хранить временные результаты в оперативной памяти или `/tmp`.
- Минимизировать запись во флеш роутера.
- Корректно завершать зависшие проверки.

## 10. Критерии завершения

Версия 2.0 считается готовой, когда:

1. Создан отдельный GitHub-репозиторий.
2. Site Checker 1.0 остался неизменённым.
3. Полностью удалён старый двойной механизм проверки сайтов.
4. Интегрирован единственный механизм Zapret Manager.
5. Сохранён выбор проверяемых сайтов.
6. Автоматически определяется установленный обходчик.
7. Используется именно его родная диагностика.
8. Отображаются версии, DNS, FakeIP и состояние приложения.
9. При отсутствии проблем выводится «ВСЁ ОК».
10. При наличии проблем выводятся только недочёты.
11. Реализован раздел «Куда пойдёт запрос».
